我平常會依照事情的複雜程度，決定怎麼使用 Agent。 比較明確、範圍也比較小的工作，我通常會直接交代需求，讓它協助處理。 如果是牽涉到多個元件、資料管理方式，或是需要考慮整體架構的功能，我就會先跟 AI 討論，確認方向之後再開始實作。 實際使用的範圍不只是寫程式。 例如 UI 實作，可以請 Agent 協助把需求轉成畫面；調整程式碼時，可以先請它分析現有的寫法，再評估怎麼修改比較合適。 遇到問題時，也可以請它協助分析可能出錯的原因，縮小排查範圍。 對我來說，Claude Code 比較像是開發過程中的協作夥伴，可以幫我加快處理事情的速度，也讓我有更多時間去思考功能本身的需求和設計。 接下來，我會先介紹一個我最近使用的設計工具，再分享兩個實際工作上的案例，看看 AI 除了寫程式之外，還能怎麼幫助我們處理開發過程中的問題。

專案當時遇到一個問題，就是新頁面的設計圖跟既有畫面風格不一致，但是專案又沒有一份完整的 UI 規範可以直接參考。 有些元件是沿用專案原本的寫法，有些則是不同時期各自撰寫的，所以實際做出來的畫面，有時候會跟環工原本想像的不太一樣。 遇到這種情況時，就需要反覆確認，到底應該沿用專案原本的樣式，還是依照這次的設計圖實作。 因為專案裡已經累積不少元件，如果要全部人工逐一盤點，再整理成文件，也需要花不少時間。 所以後來我就請 AI 協助盤點專案裡的 UI 元件。 先整理目前有哪些元件、各自怎麼使用，以及哪些地方的寫法一致、哪些地方又有不同。 再把這些資訊整理成一份 UI 元件圖鑑。 這份圖鑑不是要直接取代原本的程式碼，而是把專案裡既有的元件和樣式整理出來，讓大家有一個比較明確的參考依據。 整理完成之後，遇到設計圖跟既有畫面不一樣的情況，就可以直接拿這份圖鑑來討論。

這一頁就是整理成圖鑑之後，實際使用的方式。 圖鑑裡每個樣式旁邊都有標示。「標準」代表這個樣式在專案中大量使用，或已經做成共用元件；「待收斂」則代表只有少數地方在使用。 跟環工溝通時，我會優先推薦標準樣式。待收斂的樣式先標示出來，等之後剛好處理到相關功能時再處理。 例如 6.3 的匯出按鈕就有兩種樣式。我會等下次修改到匯出功能時，再詢問環工是否要收斂，把待收斂的樣式改成標準樣式，避免畫面一次變動太大。 之後遇到設計圖跟現有畫面不一樣的地方，我就可以在 Issue 裡說明差異，並附上可以參考的元件規範，讓環工確認要採用哪一種方式。 基本上就是兩種選擇。 第一種，是遵循專案原本的慣例，直接使用既有的元件樣式。 第二種，如果這次的設計確實有新的需求，就依照設計稿建立新的樣式，再把它整理進圖鑑裡。 這樣一來，雙方就不用每次都從頭討論，因為已經有具體的畫面可以參考。 以前遇到這類 UI 樣式確認的問題，經常需要來回溝通五次以上。 而且有些畫面細節，真的很難只靠文字說清楚。 例如字體、顏色、間距、圓角這些東西，如果全部用文字描述，不但很麻煩，也不一定能讓雙方理解得一樣。 使用這個方法之後，這類溝通通常一到兩次就能確認。 因為環工可以直接參考圖鑑，選擇要沿用既有樣式，還是建立新的規範。 除了減少溝通次數之外，也可以把專案既有的 UI 逐步整理起來，讓樣式慢慢收斂，避免後續出現越來越多種不同的寫法。 我覺得這個案例很有意思，因為 AI 在這裡不只是幫我寫程式，而是協助我整理資訊，讓原本不容易說清楚的問題，有一個具體的參考依據。 這樣大家比較容易討論，也比較容易達成共識。 接下來再分享另一個案例，這次就比較偏向實際開發。

08 / 10

專案裡有一個縣市地圖的功能，是使用 D3.js 來繪製地圖。 這張地圖會標示不同開發案場的位置，但原本的地圖主要只顯示該縣市的範圍。 問題是，有些案場雖然歸這個縣市管理，實際位置卻可能在很遠的地方。 例如高速公路，或是離岸風機。 如果地圖只顯示單一縣市的範圍，這些案場就可能落在地圖外面，沒辦法正常呈現。 當時我先看過環工提供的需求簡報，想到一個可能的解決方向，就是讓地圖的範圍涵蓋所有案場。 不過，這樣做也會有另一個問題，因為需要顯示的範圍變大，整張地圖可能會縮小。 整個畫面變動幅度有點大，所以當時我也不確定，這樣的呈現方式是不是符合需求。 如果要先把 D3.js 的相關文件全部研究完，再開始實作，可能又要花不少時間。 因此，我就先請 AI 協助做出一個初版畫面。 這個初版不一定是最後的成果，主要是希望先把想法具體呈現出來，讓大家可以直接看著畫面討論。 後來我就把這個畫面帶到會議上，跟環工確認。 環工看過之後，覺得這個方向可行，也建議可以再增加拖拉和縮放的功能，讓使用者能夠更方便地查看地圖。 這樣一來，至少核心的呈現方向就可以先取得共識，後續也有比較明確的開發方向。 我覺得這個做法滿有幫助的。 因為如果一開始只有文字描述，大家對同一個需求可能會有不同的想像。 但先做出一個可以看的畫面之後，就可以直接針對畫面討論，哪裡需要調整、哪個方向比較合適。 如果沒有先做出這個初版，我想這個問題可能還需要花更多時間來回確認。 所以這個案例讓我發現，AI 不一定要等到正式開發時才開始使用。 有時候，在需求還沒有完全確定的時候，就可以先請它協助做出一個雛形，讓後續的討論更有效率。
