這個案例是我沒有設計圖時，平常會使用的一種方式。 一開始，我會先描述功能需求，提供文字想法。 我不一定會在這個階段就把所有視覺細節都想清楚，而是先讓 Claude Design 提供幾種不同的方向。 接著，我會自己看過這些方向，選擇其中一個，再確認是不是我要的方向。 確認沒有問題之後，我就會請 Claude Code 直接進行實作。 實作完成後，我不會只看 AI 回報說已經完成，就認為事情結束了。 我會自己打開畫面實際操作，確認做出來的東西是不是符合原本的想法。 如果發現有落差，我會先自己想清楚問題在哪裡，再把問題描述給 AI，請它繼續修改。 對我來說，這是一種滿方便的工作方式。 因為我可以先從一個還沒有完全定型的想法開始，透過 AI 探索方向，再逐步把它做成可以操作的畫面。 不過，這個過程還是需要我自己做選擇，也需要實際確認結果。 AI 可以幫忙產生不同的可能性，但最後要做成什麼樣子，還是需要有人判斷。

另一個我覺得很有感的案例，不只是讓 AI 幫我寫程式，而是讓 AI 幫我整理原本工作中比較麻煩的問題。 之前有遇過一種情況，就是程式做出來可以正常運作，但畫面和 PM 想像的樣子有落差。 這個問題不完全是程式有沒有寫對，因為專案本身沒有明確的 UI 規範，有些樣式是依照過去的做法，有些地方則是各自撰寫。 所以當設計圖和實際畫面不一樣時，有時候就會遇到一個問題：到底應該遵循專案原本的做法，還是應該依照這次的設計建立新的樣式？ 後來我想了一個方法，就是請 AI 幫忙盤點專案裡的 UI 元件。 我讓它整理目前有哪些元件、使用方式是否一致，以及哪些地方是各自撰寫樣式。 整理完之後，再把這些資訊做成一份 UI 元件圖鑑。 這樣遇到設計圖和現有畫面不一樣的地方時，我就可以在 Git 留言，說明這個部分和設計圖不同，但專案目前有既有的慣例，可以參考圖鑑中的哪一個項目。 如果希望依照設計稿建立新的規範，也可以在 Git Issue 裡面說明，讓 PM 用 checkbox 確認。 這樣就不需要每次都從頭討論，也能把原本比較模糊的事情，變成有依據、可以確認的選擇。 以我的經驗，這類溝通通常一至兩次內就可以解決。 我覺得這個案例很有意思，因為 AI 在這裡不只是幫我產生程式碼，而是協助我整理資訊，讓原本比較模糊的問題更容易被討論和確認。

前面分享了兩個我平常使用 AI 的實戰案例。 但大量使用之後，我也慢慢發現一件事情，就是程式能跑，不代表事情真的做對了。 有時候 AI 產出的東西可以正常執行，但實際結果和需求還是有落差。 像剛剛提到的 UI 案例，就算畫面已經做出來了，也不代表它真的符合 PM 想要的樣子。 所以我現在還是會自己確認功能是否符合需求、能不能正常運作。 另外，我也會看程式碼本身的結構。 例如，我會在意狀態應該放在 store，還是把某些邏輯整理成 composable，也會注意整體架構是不是符合專案原本的慣例。 如果 AI 做出來的結構不符合我的想法，我通常會直接告訴它應該怎麼調整，再閱讀修改後的程式碼，確認實際功能。 所以 AI 確實幫我完成了很多實作工作，但審查、除錯，以及確認成果是否正確，還是需要時間。 這是我大量使用之後，覺得很實際的一個體會。
