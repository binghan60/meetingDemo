我平常會依照事情的複雜程度，決定怎麼使用 Agent。 比較明確、範圍也比較小的工作，我通常會直接交代需求，讓它協助處理； 如果是牽涉到多個元件、資料管理方式，或是需要考慮整體架構的功能，我會先跟 AI 討論，確認方向之後再開始實作。 實際使用的範圍也不只是寫程式。 例如 UI 實作，可以請 Agent 協助把需求轉成畫面；調整程式碼時，可以先請它分析現有的寫法，再評估怎麼修改比較合適。遇到問題時，也可以請它協助分析可能出錯的原因，縮小排查範圍。 不過，這些工作有 Agent 協助，不代表結果就一定正確。它提出的修改方式可能不符合專案原本的設計，也可能忽略需求中的細節，所以我還是需要確認修改內容，並實際驗證功能。 對我來說，使用 AI 的重點不是把所有工作都交出去，而是找到適合讓它協助的部分，減少重複性的工作，把時間留給需求判斷、設計和結果確認。 接下來，我會分享常用的設計工具，以及在工作中怎麼使用 Agent、中間遇到什麼問題，那最後是如何解決的。

接下來想介紹一個我覺得很好用的工具，叫做 Claude Design。 他的使用方式是直接在 Claude Code 打 /design，他就會問我今天想要設計什麼。 它跟一般聊天式的 AI 不太一樣，除了可以透過對話描述需求，也可以直接產生視覺化的設計，讓我們在畫布上查看成果，再繼續調整。 我自己會把它當成一個協助思考 UI 的工具。當我還不確定畫面應該怎麼排，或是有幾種不同的設計方向時，可以先請它協助我探索，而不一定要馬上開始改程式碼。

當時專案有一個常見的問題，就是設計圖跟既有畫面有時候不一致，但又沒有一份完整的 UI 規範可以直接參考，導致最後做出來的畫面跟環工原本想像的不一樣。 當遇到這種情況時，就需要反覆確認，到底應該沿用原本的樣式，還是依照這次的設計稿調整。 後來我請 AI 幫忙盤點專案裡的 UI 元件，整理目前有哪些元件、用法是否一致，以及哪些地方使用了不同的樣式，再把這些資訊整理成一份 UI 元件圖鑑。 之後遇到設計圖跟現有畫面不一樣的地方，我就可以在 Issue 裡說明差異，並附上可以參考的元件規範，讓環工選擇要遵循既有慣例，還是依照設計稿建立新的規範。 使用這個方法之前，這類問題經常需要來回溝通五次以上。而且在溝通過程中，很多畫面細節很難只靠文字說清楚，不太可能每個項目的字體、顏色、間距、圓角，都逐一描述清楚。 使用這個方法之後，這類溝通通常一到兩次就能解決。 因為環工需要做的事情變得很簡單，基本上就是兩種選擇： 第一，從 UI 元件圖鑑中挑選符合需求的既有樣式。 第二，如果設計圖有新的需求，就把這個樣式加入圖鑑，作為新的規範。 這樣一來，原本需要反覆確認、很難用文字說清楚的細節，就有了具體的參考依據，也能減少來回溝通的次數。 除此之外也可以將專案的 UI 列管，讓樣式逐步收斂，避免樣式版本越來越多種。 我覺得這個案例很有意思，因為 AI 在這裡不只是幫我寫程式，而是協助我整理資訊，把原本不容易說清楚的問題，轉變成有依據、可以選擇，也更容易達成共識的流程。
